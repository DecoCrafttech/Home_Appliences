# Admin PWA progress

Last verified: 2026-10-21. The Admin PWA is **not complete**.

## WORKING

- New `apps/admin-pwa` React/Vite/TypeScript application builds as a PWA and uses the existing Express backend.
- Staff records support five constrained roles. There is no public signup endpoint.
- A one-time `npm run admin:bootstrap -w @home/api` command creates the first `SUPER_ADMIN` only when no staff exists; later staff creation must use an authorized workflow.
- Admin login uses a unique, case-insensitive username instead of an email address. Passwords use Argon2id hashes; legacy scrypt hashes remain verifiable for migration. Login requires password verification and a short-lived MFA challenge.
- The initial `Alex` `SUPER_ADMIN` account exists in the isolated Neon development branch and its full username/password/MFA/session flow was verified against the running API. It is flagged for a required password change.
- Staff sessions use revocable HttpOnly, SameSite=Strict cookies with a 12-hour expiry.
- Unauthenticated callers are rejected from admin APIs; status mutation additionally requires an operations-capable role.
- Dashboard summary returns actual Neon customer, request, completion, pending, and open-ticket counts. Revenue is omitted because payment data is unavailable.
- Request list uses backend limit/offset pagination and joins actual customer/request rows.
- Request detail returns the shared request and real status timeline.
- Status transitions are explicitly validated, use optimistic version checks, and atomically write the request, customer-visible timeline event, and audit record through one PostgreSQL statement.
- Admin status updates are visible through the same timeline table used by the customer PWA.
- Admin UI provides login/MFA, dashboard, requests, request details, status changes, loading/error/empty states, and server-confirmed Sonner messages.
- Admin manifest and service worker are generated by the production build without runtime caching of API responses.

## FAILED / INCOMPLETE

- The first-login password-change screen and endpoint are not implemented yet, although the account is flagged with `must_change_password`.
- Technician CRUD, verification, skills, availability, conflict checks, and assignment are not implemented.
- Admin support ticket replies, ticket assignment, priorities, and customer-visible message threads are not implemented.
- Customer, catalogue, pricing, scheduling, service-area, notification, report, staff-management, and settings screens are not implemented.
- Dedicated 401/403/500/network/session-expired/maintenance/offline pages and a React error boundary are incomplete.
- Request filters/search/sorting/CSV and TanStack Table are not implemented; current pagination is API-driven but the first UI only requests one page.

## BLOCKED

- Production MFA delivery needs an approved email/SMS/authenticator provider. Development MFA is fixed to `123456` and is not returned in production.
- Payments, refunds, commissions, and revenue reports require a configured payment provider and verified transaction data.
- Technician document uploads require the secure Object Storage upload/access API.
- Production deployment and migration await review; all work is on `codex-customer-dev`.

## NOT TESTED

- Playwright browser flows, responsive visual regression, install prompts, offline navigation, and service-worker updates.
- Two simultaneous admins racing the same status transition (the version guard is integration-tested only sequentially).
- Cross-role permission combinations beyond unauthenticated access and `OPERATIONS_MANAGER` status permission.
- Production MFA, production deployment, technician assignment, support replies, and Object Storage.
